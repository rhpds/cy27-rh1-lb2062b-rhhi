[[introduction]]
== Introduction

Vulnerability scanning tells you about known CVEs today, but software supply chain compliance also requires you to understand what is in your images. A Software Bill of Materials (SBOM) is that inventory.
SBOMs should not only be supplied by the vendor for the base image, but also created for any derived images separately.
This is how a chain of trust is built and extended, where each link can be checked in both directions.

SBOMs are essential for:

* **Supply chain security** — know exactly what packages and libraries are in your images
* **Compliance** — meet regulatory requirements like NIST SP 800-218, the EU Cyber Resilience Act, and Executive Order 14028
* **Vulnerability management** — when a new CVE is disclosed, quickly identify which images are affected without re-scanning everything

[[human-readable]]
== Step 1: View a Human-Readable Package Table

Syft can generate a quick summary in table format. 
Let's see what's in `rhhi-demo:hardened`:

[source,bash,role=execute]
----
syft rhhi-demo:hardened -o table
----

.*Expected output (excerpt):*
----
NAME                VERSION    TYPE
flask               3.1.1      python
werkzeug            3.1.3      python
click               8.1.8      python
jinja2              3.1.5      python
markupsafe          3.0.2      python
itsdangerous        2.2.0      python
blinker             1.9.0      python
...
python3             3.12.13    rpm
python3-libs        3.12.13    rpm
glibc               2.34-125   rpm
openssl-libs        3.2.2-6    rpm
----

Notice that Syft identifies not just RPMs from the included rpmdb, but the application dependencies.

* `python` packages — Flask and its runtime dependencies installed via pip
* `rpm` packages — system libraries from the hardened base image

This is another way to quickly examine a distroless image when standard tricks like `rpm -qa` aren't available.

The page for a specific base image, https://images.redhat.com/?name=python&tab=sbom[the python runtime for example^], will also show an SBOM tab with a search box if you are looking for any particular package or library in a published runtime.
There's also a link to the published SPDX, we'll talk more about that format next.
[TIP]
====
Having access to vendor provided SBOMs and being able to create SBOMs for your applications are important to the verification of created images.
====

[[spdx-sbom]]
== Step 2: Generate a Machine-Readable SPDX SBOM

A table is useful for human review, but compliance workflows need machine-readable output. 
There are several standard SBOM formats; we'll use Software Package Data Exchange (SPDX), an ISO/IEC standard (ISO/IEC 5962:2021).

Generate the SBOM for our Flask application:

[source,bash,role=execute]
----
syft rhhi-demo:hardened -o spdx-json=~/rhhi-demo.spdx
----

.*Expected output:*
----
 ✔ Loaded image                                           rhhi-demo:hardened
 ✔ Parsed image  sha256:9b2e4f6a...
 ✔ Cataloged contents   a3c7d9e1...
   ├── ✔ Packages                        [68 packages]  
   ├── ✔ Executables                     [184 executables]  
   ├── ✔ File metadata                   [3,064 locations]  
   └── ✔ File digests                    [3,064 files]  
----

[[inspect-sbom]]
== Step 3: Inspect the SBOM

The SPDX format is a JSON file. Use `jq` to query it for the number of packages installed:

[source,bash,role=execute]
----
jq '.packages | length' ~/rhhi-demo.spdx
----

.*Expected output:*
----
69
----

[NOTE]
====
The package count from `jq` may differ slightly from Syft's cataloged count because the SPDX format includes the image itself as a top-level package entry alongside its contents. Images are still being reviewed to remove unnecessary packages, which may also change package counts from the time of writing.
====

Look up a specific package by name to see what the SBOM records about it:

[source,bash,role=execute]
----
jq '.packages[] |
  select(.name == "flask") |
  {name, versionInfo, sourceInfo}' \
  ~/rhhi-demo.spdx
----
[source,json]
----
{
  "name": "flask",
  "versionInfo": "3.1.3",
  "sourceInfo": "acquired package info from installed python package manifest file: /usr/local/lib/python3.12/site-packages/flask-3.1.3.dist-info/METADATA, /usr/local/lib/python3.12/site-packages/flask-3.1.3.dist-info/RECORD"
}
----
The `sourceInfo` field shows where syft found the package — pip-installed Python packages come from their dist-info metadata, while RPM packages come from the RPM database.
That distinction is how the SBOM captures both layers of the image in the same format.

[[sbom-formats]]
== SBOM Formats

[NOTE]
====
**Supported SBOM formats in Syft:**

* **SPDX-JSON** (`spdx-json`) — ISO/IEC 5962:2021, widely supported by compliance tools
* **CycloneDX** (`cyclonedx-json`) — OWASP standard, popular in DevSecOps pipelines
* **Table** (`table`) — human-readable, for quick review
* **JSON** (`json`) — Syft's native format with additional metadata

For compliance requirements, use `spdx-json` or `cyclonedx-json`. Both formats are accepted by tools like FOSSA, Dependency-Track, and grype.
====

== Summary

You've catalogued exactly what's in `rhhi-demo:hardened` and saved a machine-readable inventory at `~/rhhi-demo.spdx`.
That file is the artifact you'll return to in a later exercise — it becomes a signed attestation attached to the image in the registry, so consumers can verify both the image and its contents against the same key.

You know what's in the image.
The next exercise establishes where it came from.
