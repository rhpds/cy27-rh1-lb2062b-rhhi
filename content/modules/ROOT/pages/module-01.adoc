= Vulnerability Scanning Container Images

.*Module Overview*
[sidebar]
--
*Objectives:*

[[introduction]]
== Introduction

Every image in this lab comes from Red Hat, a trusted source.
The question this module answers is not *whether* to trust that source, but *which* starting point gives an application the cleanest foundation to build on.
A base image you inherit carries its packages -- and every CVE in them -- into everything you ship on top of it.
Choosing a low-noise baseline means fewer vulnerabilities to triage for the life of the application.

You'll use industry-standard tools to measure that noise for two different starting points.
Two application images are pre-built and waiting for you:

* `rhhi-demo:hardened` — a Flask web app built using Red Hat Hardened Images as the runtime base (`hi/python:3.12`), using the included `pip` to install the application dependencies. 
* `rhhi-demo:ubi` — the same Flask app built from the standard UBI10 base image (`ubi10/ubi`) with Python 3.12 and pip installed via dnf, a common real-world pattern for containerizing Python applications

Both images run the same application code and the same version of Python 3.12. 
The only difference is the base image. 
You'll use `grype` to scan both for known CVEs and see firsthand how the choice of base image affects your security posture.
You'll also create and explore the Software Bill of Materials (SBOM) for a container image in a later section.

[[podman-socket]]
== Step 1: Enable the Podman Socket

Grype and Syft use the Podman API socket to find and inspect images. 
As a rootless user, you can enable this socket just for your session — you don't need system-level access.

[source,bash,role=execute]
----
systemctl --user enable --now podman.socket
----

[NOTE]
====
This enables the socket for the current user session only. It does not require `sudo` or root privileges. This is a key feature of rootless Podman: the daemon socket runs entirely within your user namespace.
====

[[scan-hardened]]
== Step 3: Scan the Hardened Image

Use Grype to scan `rhhi-demo:hardened` locally for known CVEs:

[source,bash,role=execute]
----
grype rhhi-demo:hardened --by-cve
----

The scan may take 1-2 minutes to complete. 
The `--by-cve` flag normalizes output to CVE identifiers instead of other data sources like GHSA, making it easier to cross-reference with other tools and databases.

.*Expected output (varies, but typically):*
----
 ✔ Loaded image                                           rhhi-demo:hardened
 ✔ Parsed image sha256:9b2e4f6a...
 ✔ Cataloged contents  a3c7d9e1...
   ├── ✔ Packages                        [68 packages]  
   ├── ✔ File digests                    [3,064 files]  
   ├── ✔ Executables                     [184 executables]  
   └── ✔ File metadata                   [3,064 locations]
 ✔ Scanned for vulnerabilities     [0 vulnerability matches]
   ├── by severity: 0 critical, 0 high, 0 medium, 0 low, 0 negligible
   └── by status:   0 fixed, 0 not-fixed, 0 ignored
No vulnerabilities found
----

[IMPORTANT]
====
Hardened base images typically have **zero or near-zero CVEs** at ship time. Results may vary over time as new CVEs are discovered and reported against any component.
====
The two key lines in the output header are *severity*, providing a count of detected CVEs, and *status*.
Status shows a high level view of what has a fix available but not applied, what is still awaiting a fix, and what `grype` was told to skip.
The full status of any CVE for any hardened image can be found either on the specific image page or in https://images.redhat.com/security-feed[the full CVE feed^].
[[scan-ubi]]
== Step 4: Compare with the UBI Image

Now scan the UBI-based version to see the difference:

[source,bash,role=execute]
----
grype rhhi-demo:ubi --by-cve 
----

.*Expected output (varies, but typically):*
----
 ✔ Loaded image                                           rhhi-demo:ubi
 ✔ Parsed image  sha256:8f3a1c2d...
 ✔ Cataloged contents   58f3a1c2d..
   ├── ✔ Packages                        [201 packages]  
   ├── ✔ Executables                     [642 executables]  
   ├── ✔ File metadata                   [7,199 locations]  
   └── ✔ File digests                    [7,199 files]  
✔ Scanned for vulnerabilities     [252 vulnerability matches]  
   ├── by severity: 0 critical, 2 high, 134 medium, 116 low, 0 negligible
   └── by status:   0 fixed, 252 not-fixed, 0 ignored 
<output truncated>
----

Since UBI follows RHEL, there will likely be some number of Low and Medium CVEs that haven't been addressed.
While it is likely these may be difficult to trigger in a containerized environment, this still represents work needed to evaluate that likelihood. 
Depending on the scanners used, risk triage will vary and severity may not match that https://access.redhat.com/security/updates/classification[assigned by Red Hat^].
This type of cross-team toil is exactly what Red Hat Hardened Images aims to remove from the development lifecycle.

The `--only-fixed` flag shows only vulnerabilities that have available patches. 
This focuses attention on immediately actionable issues rather than those currently under investigation, deferred, or `wontfix` items. 

[source,bash,role=execute]
----
grype rhhi-demo:ubi --by-cve --only-fixed
----
[source,bash,role=execute]
----
grype rhhi-demo:hardened --by-cve --only-fixed
----
Notice that while the list changes, the header reported identical information.
This is only an output filter.

[TIP]
====
This flag and others will filter the output for any scan. The full options and outputs for `grype` are outside the scope of this lab.
====

**Key Insight:**

Both starting points come from the same trusted source; the difference is the *noise* each one hands you to triage.

* **Hardened image** (`rhhi-demo:hardened`): Minimized image tracking upstream to deliver new images as quickly as changes are available. Few packages means the CVEs that do appear are real signal.
* **UBI image** (`rhhi-demo:ubi`): General purpose base image tracking RHEL to deliver backported fixes for maximum flexibility and supportability. A larger package set carries a long low/medium tail -- often unreachable, awaiting a backport -- that still costs triage effort to evaluate.

Both images run the same Flask app on the same Python.
The CVE difference comes entirely from the base image — the hardened runtime includes only what a Python application needs at runtime, while even a minimal UBI base carries package management infrastructure and general-purpose system tools. 
Every extra package is a potential CVE surface.
Within the UBI family, there are additional types beyond the standard image used here that also address this sort of package reduction.

Both images include the Python dependencies for Flask (`pip install flask`), so any CVEs in the application would be common.

[[summary]]
== Summary

The choice of starting point can greatly impact the amount of triage required by teams to secure an application.
Starting from a low-noise baseline is the first link in a chain you'll extend through the rest of this lab: a clean foundation you can inventory, verify, and carry forward with confidence.
While this is not the only factor when considering base image choices, it's important to understand how the different life cycle choices influence the results.
