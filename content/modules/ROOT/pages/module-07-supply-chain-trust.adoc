[[introduction]]
== Introduction

Across this lab you've built your own links in a chain: you scanned a baseline, inventoried it with an SBOM, verified signatures, signed your image, and attached a signed SBOM attestation.
Every one of those links is something Red Hat also produces for the images you inherited.

This module looks at the link that sits *before* yours -- the build provenance the source attaches to prove not just *that* an image is authentic, but *how and where* it was built.
The framework for that is *SLSA* (Supply-chain Levels for Software Artifacts), which formalizes build-integrity metadata as a signed attestation traveling with the image.

[[download-vendor-attestation]]
== Download the Vendor's Attestations

In Module 6 you attached and downloaded an attestation for your own image. Red Hat publishes attestations for its images the same way, and you can download them with the same command.

[source,bash,role=execute,subs=attributes+]
----
cosign download attestation --output-file redhat.sbom \
  {rhhi-registry}/python:3.12
----

Notice the file type is slightly different than the single attestation you attached.

[source,bash,role=execute]
----
file redhat.sbom
----
....
redhat.sbom: New Line Delimited JSON text data
....

Each line is a separate DSSE envelope. Red Hat's images carry more than one kind of provenance in this bundle, so list the predicate type of each envelope to see what's inside.

[source,bash,role=execute]
----
jq -r '.payload | @base64d | fromjson | .predicateType' redhat.sbom
----
.*Expected output:*
....
https://spdx.dev/Document
https://slsa.dev/provenance/v0.2
....

The first is an SBOM, the same kind of package inventory you worked with in Module 2.
The second is the *SLSA build provenance* -- the record of how the image was produced. That's the one we'll examine.

[[isolate-slsa]]
== Isolate the SLSA Provenance

The bundle holds both predicates, so select the SLSA envelope by its predicate type, decode it, and save the in-toto statement to its own file.
`jq` reads the newline-delimited envelopes one at a time; `@base64d` decodes the payload without a separate `base64` step.

[source,bash,role=execute]
----
jq -r '
  select((.payload | @base64d | fromjson | .predicateType) == "https://slsa.dev/provenance/v0.2")
  | .payload | @base64d | fromjson
' redhat.sbom > ~/python-slsa.json
----

Confirm you captured a single SLSA statement.

[source,bash,role=execute]
----
jq -r '.predicateType' ~/python-slsa.json
----
....
https://slsa.dev/provenance/v0.2
....

[NOTE]
====
Red Hat emits SLSA provenance at *v0.2*, generated by its Tekton Chains build system. The current published specification is v1.x; the concepts are the same, but the exact field names below are the v0.2 names present in this attestation.
====

[[inspect-slsa]]
== Inspect the Build Provenance

The predicate answers four practical questions about the image's origin.

*Who built it?* The builder identity is the system that produced the attestation.

[source,bash,role=execute]
----
jq -r '.predicate.builder.id' ~/python-slsa.json
----
....
https://tekton.dev/chains/v2
....

*How was it built?* The build type and whether the build was *hermetic* -- run with no unexpected network access, so the inputs are exactly what's declared.

[source,bash,role=execute]
----
jq -r '.predicate.buildType' ~/python-slsa.json
jq -r '.predicate.invocation.parameters.hermetic' ~/python-slsa.json
----
.*Expected output (varies):*
....
tekton.dev/v1/PipelineRun
true
....

*When was it built?* The metadata records the build window.

[source,bash,role=execute]
----
jq '{started: .predicate.metadata.buildStartedOn, finished: .predicate.metadata.buildFinishedOn}' ~/python-slsa.json
----

*What went into it?* The `materials` are the inputs to the build -- source, build tools, and task images -- each pinned to an immutable digest. Count them to see the breadth of what's recorded.

[source,bash,role=execute]
----
jq '.predicate.materials | length' ~/python-slsa.json
----
.*Expected output (varies):*
....
39
....

You can look at an individual material to see the pinned digest.

[source,bash,role=execute]
----
jq '.predicate.materials[0]' ~/python-slsa.json
----

Every input is recorded with an immutable digest, and the build was hermetic, so the provenance is more than a description -- it's a *recipe you can reproduce*.
Because the source, the build tools, and the parameters are all pinned, you (or an auditor) can reconstruct the same inputs and re-run the build locally.
A deterministic build then yields the same image digest, letting you *independently confirm* the vendor's image is exactly what its provenance claims -- rather than taking the vendor's word for it.
That is the difference between provenance you can read and provenance you can *verify by rebuilding*.

[[mirror-and-provenance]]
== Provenance and the Mirror Gap

This provenance is attached to the vendor image the same way the signature was -- as a separate artifact beside the image in the registry.
When you mirrored `python:3.12` into your own registry in Module 4, this provenance, like the signature, stayed behind.

[NOTE]
====
With other tools it is possible to carry this attestation along with the mirrored image, but that is outside the scope of this lab.
====

[[summary]]
== Summary

You've now seen every kind of link in the chain, from both sides.

* *Scanning* (Module 1) -- the source publishes a CVE feed so you can measure the noise in a baseline before you build on it.
* *SBOM* (Modules 2, 6) -- the source publishes package inventories; you generate and attest your own.
* *Signatures* (Modules 3, 5) -- the source signs what it publishes; you sign what you ship and re-sign what you mirror.
* *Build provenance* (this module) -- the source attaches SLSA provenance describing how its images were built, with enough pinned detail to reproduce the build and confirm the result yourself.

Supply-chain security isn't any single one of these tools. It's an unbroken, inspectable chain from a trusted source, through your build, to whoever consumes what you ship -- where every link can be examined and every handoff keeps the chain intact.

.*Production Best Practices*

* Verify vendor provenance as part of image admission, not just signatures.
* Record and retain provenance for your own builds so downstream consumers can inspect your links too.
* Prefer hermetic builds -- provenance is only as trustworthy as the build that produced it.
* Track the SLSA specification level your build system emits, and raise it over time.
