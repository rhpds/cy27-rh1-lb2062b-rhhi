= Establishing Supply Chain Trust

.*Module Overview*
[sidebar]
--
*Objectives:*

* Download the attestations Red Hat publishes for a vendor image
* Inspect the SLSA build provenance to evaluate build identity, build environment controls, and input materials
* Trace the image back to its source commit in a public repository
--

[[introduction]]
== Introduction

Across this lab you've built your own links in a chain: you scanned a baseline, inventoried it with an SBOM, verified signatures, signed your image, and attached a signed SBOM attestation.
Every one of those links is something enterprise vendors like Red Hat produce for their official images and software.

This exercise looks at **build provenance**, the record showing *how and where* an artifact was built.
The framework for that is *SLSA* (Supply-chain Levels for Software Artifacts), which formalizes build-integrity metadata as a signed attestation traveling with the image.

This is the final concept for verifying your software supply chain. 

* Which specific image am I dealing with? (Digest)
* Is that image authentic? (Signature)
* Was that image built in a secure fashion? (SLSA provenance)

[[download-vendor-attestation]]
== Download the Vendor's Attestations

Red Hat publishes attestations for its images the same way you attached one to yours -- as OCI artifacts stored alongside the image in the registry.

[source,bash,role=execute,subs=attributes+]
----
cosign download attestation --output-file redhat.att \
  {rhhi-registry}/python:3.12
----

[source,bash,role=execute]
----
file redhat.att
----
....
redhat.att: JSON text data
....

We can examine the JSON to see what's included in the attestation.
[source,bash,role=execute]
----
jq 'map_values(type)' redhat.att
----
....
{
  "payloadType": "string",
  "payload": "string",
  "signatures": "array"
}
....

The attestation is in the payload string encoded in base64.
Decoding it into a plain JSON file is a lab convenience, so the rest of this exercise can read it with simpler `jq` filters.

[source,bash,role=execute]
----
jq -r '.payload | @base64d | fromjson' redhat.att > ~/python-slsa.json
----

Listing the predicate type on the decoded file confirms the statement is the SLSA build provenance:

[source,bash,role=execute]
----
jq -r '.predicateType' ~/python-slsa.json
----
....
https://slsa.dev/provenance/v0.2
....

[NOTE]
====
Red Hat emits SLSA provenance at *v0.2*, generated by its Konflux CI build system via Tekton Chains.
The current published specification is v1.x; the concepts are the same, but the field names below are the v0.2 names present in this attestation.
====

[[inspect-builder-trust]]
== Was This Built in a Controlled Environment?

The *builder identity* names the system that produced and signed the attestation:

[source,bash,role=execute]
----
jq -r '.predicate.builder.id' ~/python-slsa.json
----
....
https://tekton.dev/chains/v2
....

Red Hat Hardened Images are built on Konflux CI, Red Hat's internal build platform.
Konflux uses Tekton Chains as its attestation component -- the part of the pipeline that signs build results and produces SLSA provenance records.
`https://tekton.dev/chains/v2` is the builder ID Tekton Chains sets by default; the https://github.com/tektoncd/chains/blob/main/docs/config.md[Tekton Chains configuration documentation^] shows how it is defined and how operators can change it.
When evaluating a third-party image, this is the field you'd check: does the builder ID match what that vendor documents as their build infrastructure?

The *hermetic flag* describes what the build was permitted to do at runtime:

[source,bash,role=execute]
----
jq -r '.predicate.invocation.parameters.hermetic' ~/python-slsa.json
----
....
true
....

A hermetic build runs without network access during the build itself.
You will see why this matters when you look at the git commit and the materials -- the dependency specifications in the source repository are what the build was constrained to, and the hermetic flag is the assertion that nothing outside them entered.

[[trace-to-source]]
== Trace This Image Back to Source

The `materials` field records every input to the build: source code, build tools, and pipeline task images.
The most important entry is the source git commit -- the traceable link between the binary you've been working with and the exact revision of code that produced it.

[source,bash,role=execute]
----
jq '.predicate.materials[] | select(.uri | startswith("git+"))' ~/python-slsa.json
----
.*Expected output (commit hash varies by build):*
[source,json]
----
{
  "digest": {
    "sha1": "31390d26a2611ee3286679e4fedf9825e264dbe7"
  },
  "uri": "git+https://gitlab.com/redhat/hummingbird/containers.git"
}
----

That commit contains the Containerfile and the dependency specifications -- lockfiles, requirements files, or equivalent -- that define exactly what packages the build was allowed to fetch.
You can visit the repository and read exactly what went into the `hi/python:3.12` image you used as the base during the lab.
This is what "traceable back to source" means in practice, not an assertion in a document, but a direct link you can follow.

How many total inputs went into this build?

[source,bash,role=execute]
----
jq '.predicate.materials | length' ~/python-slsa.json
----
.*Expected output (varies):*
....
40
....

One is the git commit.
The others are the Konflux CI build tools -- task runners, artifact stores, the pipeline tasks themselves -- each pinned to an immutable digest.
The tool that connects the git commit to the rest of the materials list is the one that enforces the hermetic constraint:

[source,bash,role=execute]
----
jq '.predicate.materials[] | select(.uri | contains("hermeto"))' ~/python-slsa.json
----
.*Expected output (digest varies by build):*
[source,json]
----
{
  "uri": "oci://quay.io/konflux-ci/hermeto",
  "digest": {
    "sha256": "74b3099b351808ca235af3cefe167e0652e37ad41a5147507bad78aef0aabad5"
  }
}
----

`hermeto` is Konflux CI's dependency prefetching tool.
It resolves and records the dependencies listed in the git commit, then the build runs with network access cut.
`hermetic: true` is the assertion that this constraint held: the dependency spec at that git commit is the complete and only source of external inputs.

The git commit, the hermetic flag, and hermeto in the materials list point at the same thing from three directions.
Together they describe the conditions for an independently reproducible build: the source is public, the build tools are pinned by digest, the build environment is hermetic, and Konflux CI itself is a public system.
Given those inputs, you can run the same pipeline and verify that the output matches the published image digest -- rather than taking the provenance record on trust alone.
If you'd like to read more about these reproducible builds, here's a blog from an engineer that provides more details: https://developers.redhat.com/articles/2026/03/26/reproducible-builds-project-hummingbird#hummingbird_reproducibility[Reproducible Builds: Project Hummingbird^].

[[summary]]
== Summary

You've now seen every kind of link in the chain, from both sides.

* *Scanning* -- the source publishes a CVE feed so you can measure the noise in a baseline before you build on it.
* *SBOM* -- the source publishes package inventories; you generate and attest your own.
* *Signatures* -- the source signs what it publishes; you sign what you ship and re-sign what you mirror.
* *Build provenance* -- the source attaches SLSA provenance recording the builder identity, hermetic build environment, and every pinned input. With a public source repo, pinned tools, and a public build system, the provenance is the input specification for an independently reproducible build -- verification by rebuilding, not just inspection.

Supply-chain security isn't any single one of these tools.
It's an unbroken, inspectable chain from a trusted source, through your build, to whoever consumes what you ship -- where every link can be examined and every handoff keeps the chain intact.

[NOTE]
====
Provenance, like signatures, lives in the source registry as a separate OCI artifact.
Carrying attestations alongside a mirrored image is a deliberate, separate procedure outside the scope of this lab.
====

.*Production Best Practices*

* Verify vendor provenance as part of image admission, not just signatures.
* Record and retain provenance for your own builds so downstream consumers can inspect your links too.
* Prefer hermetic builds -- provenance is only as trustworthy as the build environment that produced it.
* Track the SLSA specification level your build system emits, and raise it over time.
