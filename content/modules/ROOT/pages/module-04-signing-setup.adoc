= Image Signing Setup

.*Module Overview*
[sidebar]
--
*Objectives:*

[[introduction]]
== Introduction

In the previous exercise you verified that `hi/python:3.12` — the base your application is built from — carries a valid Red Hat signature.
That verification happened against the image in Red Hat's registry.

In practice, most organizations don't pull directly from vendor registries at build or deployment time.
Depending on an external registry creates availability risk: if it's slow or unreachable, builds fail.
In air-gapped and disconnected environments there's no choice — the image has to be in a registry you operate.
So you mirror it.

Mirroring isn't a neutral act.
This exercise is about what that move does to the chain you just established.

[[digests-and-tools]]
== Digests and How Mirroring Works

A container image is identified by its digest, a SHA256 hash computed over the manifest bytes.
For a multi-architecture image, that means the index manifest, which references per-platform manifests, which in turn reference the layer blobs.
Change any byte anywhere in that structure and the digest changes.

The lab environment already pulled `hi/python:3.12` from the vendor registry as part of building `rhhi-demo:hardened`.
Compare what podman has locally against what the vendor registry reports:

[source,bash,role=execute,subs=attributes+]
----
podman image inspect hi/python:3.12 --format '{{.Digest}}'
----

[source,bash,role=execute,subs=attributes+]
----
skopeo inspect docker://{rhhi-registry}/python:3.12 | jq -r .Digest
----

.*Expected output (two different digests):*
----
sha256:9f3a2c1d...
sha256:cbcfabb29dd4604204ea2bd317f356ddb3ec3ec97e210692591ad4d97db4a1cb
----

The content is identical, but the digests are different.
When podman pulled the image, it only needed the `amd64` architecture layers for this host.
The new local digest was computed from just that manifest, not the complete multi-architecture one in the registry.

A mirror that started with `podman pull` and ended with `podman push` would carry this same mismatch into your registry.
The bits arrive intact; the identity the vendor published does not.

`skopeo copy --all` copies the index and all platform manifests directly between registries without reassembling them.
`--preserve-digests` makes that an explicit commitment: copy the manifest bytes exactly as-is, fail if that isn't possible.
The result is a mirror whose digest matches the one the vendor signed.

[[local-registry]]
== Your Local Container Registry

This lab environment includes a private container registry running at `registry-{guid}.{domain}`.
It is secured with a TLS certificate issued by ZeroSSL, so standard container tools work without any insecure-registry configuration.

The registry requires no login — it is intentionally open for this lab so you can focus on signing rather than credential management.

[TIP]
====
The `REGISTRY` environment variable pointing to your local registry was set during lab setup and persists in your terminal session via `~/.bashrc`. If it isn't set in your session, run:

[source,text]
----
source ~/.bashrc
----

You can check the current value at any time with `echo $REGISTRY`.
====

[[mirror-vendor-image]]
== Mirror the Python Base Image

Let's bring `{rhhi-registry}/python:3.12` into the local registry.

[source,bash,role=execute,subs=attributes+]
----
skopeo copy --all \
  docker://{rhhi-registry}/python:3.12 \
  docker://registry-{guid}.{domain}/python:3.12
----

The image layers copy, but the command fails at the end.

.*Expected output (final line):*
----
FATA[...] copying image 1/2 from manifest list: writing signatures: writing sigstore attachments is disabled by configuration
----

Cosign signatures are OCI artifacts stored in the registry alongside the image, linked to the image's digest via the referrers API.
They are not embedded in the image itself — they live beside it in the source registry.
When `skopeo copy` moves the image, it also attempts to carry those artifacts across.
The destination registry in this lab doesn't accept referrer-linked artifacts, so the copy can't finish.

The pattern this lab follows is: verify at the source, mirror the image with its digest intact, then re-sign with an internal key.
You verified in the previous exercise that this image is exactly what Red Hat published.
You'll mirror it now, preserving that digest as proof of what you received, and re-sign it in the next exercise so your registry's admission policies have something to check.
The vendor's original signature doesn't make the trip — what you're establishing is your own chain of custody from this point forward.

[NOTE]
====
This isn't the only approach, and tooling is improving.
Rather than dropping vendor signatures when re-signing, some teams preserve both: the vendor signature stays intact and an internal signature or attestation is appended alongside it — for example, a cosign attestation that includes vulnerability scan results.
In-cluster admission policies can then enforce a two-key requirement: vendor origin identity plus internal security review identity.
This preserves provenance all the way through the chain rather than replacing it.
====

For now, tell `skopeo` to leave the signatures behind.

[[keep-the-digest]]
== Copy With a Preserved Digest

Run the copy again with `--remove-signatures` to leave the vendor's signatures in the source registry, and `--preserve-digests` to copy the manifest without rewriting it.
The `--digestfile` flag records the resulting digest.

[source,bash,role=execute,subs=attributes+]
----
skopeo copy --all --preserve-digests --remove-signatures \
  --digestfile ~/python.digest \
  docker://{rhhi-registry}/python:3.12 \
  docker://registry-{guid}.{domain}/python:3.12
----

Now compare the digest in your mirror against the one at the source:

[source,bash,role=execute,subs=attributes+]
----
skopeo inspect docker://{rhhi-registry}/python:3.12 | jq -r .Digest
skopeo inspect docker://registry-{guid}.{domain}/python:3.12 | jq -r .Digest
----

.*Expected output (both lines identical):*
----
sha256:cbcfabb29dd4604204ea2bd317f356ddb3ec3ec97e210692591ad4d97db4a1cb
sha256:cbcfabb29dd4604204ea2bd317f356ddb3ec3ec97e210692591ad4d97db4a1cb
----

Identical digests mean identical content — every layer, every byte.
Your mirror is provably the same image Red Hat published.

[[origin-is-gone]]
== Confirm the Signature Gap

You explicitly left the vendor signatures behind — run the same verification you did in the previous exercise to confirm what that means for your registry:

[source,bash,role=execute,subs=attributes+]
----
cosign verify --insecure-ignore-tlog \
  --key https://security.access.redhat.com/data/63405576.txt \
  registry-{guid}.{domain}/python:3.12
----

.*Expected output:*
----
Error: no matching signatures:

main.go:74: error during command execution: no matching signatures:
----

Expected.
The image is in your registry with its digest intact, but no signature for cosign to check.
Closing that gap — for both the vendor base and your application image — is the work of the next exercise.

[[push-image]]
== Push Your Application Image

The vendor base is in your registry.
The application image built from it — `rhhi-demo:hardened` — is still only in local podman storage.
Cosign attaches signatures as OCI artifacts in a registry, so push it alongside the base before you can sign either of them.

Tags are mutable — a tag can be reassigned to a different image at any time, which makes signing a tag meaningless.
Cosign signs digests.
The `--digestfile` flag captures the digest the registry assigns when the image is pushed, which is what you'll hand to cosign in the next exercise.

[source,bash,role=execute,subs=attributes+]
----
podman tag rhhi-demo:hardened registry-{guid}.{domain}/rhhi-demo:hardened
----

[source,bash,role=execute,subs=attributes+]
----
podman push --digestfile ~/image.digest registry-{guid}.{domain}/rhhi-demo:hardened
----

[source,bash,role=execute]
----
IMAGE_DIGEST=$(cat ~/image.digest)
echo "Image digest: ${IMAGE_DIGEST}"
----

.*Expected output:*
----
Image digest: sha256:abc123...
----

[[generate-keys]]
== Generate a Cosign Key Pair

[source,bash,role=execute]
----
export COSIGN_PASSWORD=""
----

[source,bash,role=execute]
----
cosign generate-key-pair
----

.*Expected output:*
----
Private key written to cosign.key
Public key written to cosign.pub
----

The private key is what you'll use to sign.
The public key is what consumers use to verify.
Share the public key widely; keep the private key secret.

[TIP]
====
*Cosign Key Strategies*

* *Development*: Generate local key pairs (as we do here)
* *Production*: Keyless signing with OIDC identity (GitHub, GitLab, Google)
* *Enterprise*: KMS-backed keys — AWS KMS, Azure Key Vault, GCP KMS, HashiCorp Vault
* *High security*: Hardware Security Modules (HSM)

Never commit local keys like `cosign.key` to a git repository. Always check the `cosign` documentation for https://docs.sigstore.dev/cosign/key_management/overview/[an authoritative list of keystores^].
====

== Summary

You have two images in your local registry: the vendor base you mirrored from Red Hat and your application built from it.
Neither carries a signature cosign can verify — the vendor's signature didn't make the trip, and your application image was never signed.
In the next exercise you'll sign both with your new key pair, so everything in your registry gates on a key you control.
