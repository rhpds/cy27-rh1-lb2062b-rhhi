[[introduction]]
== Introduction

We've completed half of the mirroring pattern we defined earlier.
These two images are now both under our control, but can't be verified the same way the signed original `hi/python:3.12` image can be.
The digest is the cryptographic identifier that lets us pick exact images to use.
The signature is the cryptographic 'seal of approval' that marks that exact image as authentic and verified, much like an SSL certificate does for a website.


[[generate-keys]]
== Generate a Cosign Key Pair

Cosign uses a pair of cryptographic keys for signing and verification.
The private key is what you'll use to sign.
The public key is what consumers use to verify.

We'll use a local static key pair without a password for the purposes of the lab.
This is only for this lab and not a recommendation. 
See the tip below for a brief list of potential strategies for key pair management.

[source,bash,role=execute]
----
export COSIGN_PASSWORD=""
----

[source,bash,role=execute]
----
cosign generate-key-pair
----

.*Expected output:*
----
Private key written to cosign.key
Public key written to cosign.pub
----

Share the public key widely; keep the private key secret.

[TIP]
====
*Cosign Key Strategies*

* *Development*: Generate local key pairs (as we do here)
* *Production*: Keyless signing with OIDC identity (GitHub, GitLab, Google)
* *Enterprise*: KMS-backed keys — AWS KMS, Azure Key Vault, GCP KMS, HashiCorp Vault
* *High security*: Hardware Security Modules (HSM)

Never commit local keys like `cosign.key` to a git repository. Always check the `cosign` documentation for https://docs.sigstore.dev/cosign/key_management/overview/[an authoritative list of keystores^].
====


[[sign-image]]
== Sign the Image

[NOTE]
====
The `--tlog-upload=false` flag skips uploading to the Rekor public transparency log -- as covered in the previous exercise, we skip this in lab environments to avoid adding noise to the public Sigstore instance.
====

Cosign signs by digest, not tag — a tag can be reassigned, a digest cannot.
The `@${IMAGE_DIGEST}` syntax addresses the image by the specific digest the registry computed when you pushed it.
[source,bash,role=execute,subs=attributes+]
----
cosign sign --tlog-upload=false \
  --yes --key cosign.key \
  registry-{guid}.{domain}/rhhi-demo@${IMAGE_DIGEST}
----
----
Pushing signature to: registry-{guid}.{domain}/rhhi-demo
----

The signature is stored as an OCI artifact in the same repository as your image. 
Cosign appends it as a separate manifest with a `.sig` tag suffix. 
You can see this if you list the repository tags -- the registry will show both `:hardened` and a digest-tagged signature artifact.

[source,bash,role=execute,subs=attributes+]
----
skopeo list-tags docker://registry-{guid}.{domain}/rhhi-demo
----
----
{
    "Repository": "registry-68xq6.apps.ocpvdev01.rhdp.net/rhhi-demo",
    "Tags": [
        "hardened",
        "sha256-3cadbbd0e1e98c6cf62fb783591b86997be1d1f34a8c0b30acd1f409042b6f83.sig"
    ]
}
----
[[verify-signature]]
== Verify the Signature

Just as you verified Red Hat's signatures in the previous exercise, you can now verify your own.
This is the same workflow a consumer of your image would run to confirm the image is authentic.

[source,bash,role=execute,subs=attributes+]
----
cosign verify --insecure-ignore-tlog=true \
  --key cosign.pub \
  registry-{guid}.{domain}/rhhi-demo:hardened
----
----
WARNING: Skipping tlog verification is an insecure practice that lacks of transparency and auditability verification for the signature.

Verification for registry-{guid}.{domain}/rhhi-demo:hardened --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key

[{"critical":{"identity":{"docker-reference":"registry-{guid}.{domain}/rhhi-demo"},...
----
The JSON here is much simpler than what we discarded in the previous exercise, but shows the registry, digest, and signature information.

[NOTE]
====
The sign command used a digest reference (`@${IMAGE_DIGEST}`); the verify command here uses a tag.
Both work because cosign resolves the tag to its current digest and looks for a signature attached to that digest.
A downstream consumer verifying by tag gets the same result as verifying by digest — as long as the tag hasn't been reassigned to a different image since it was signed.
====

[[resign-mirrored]]
== Re-sign the Mirrored Image

In the previous exercise you mirrored `hi/python:3.12` with its digest preserved and deliberately left Red Hat's signatures behind.
Re-signing with your own key is the second half of the mirroring pattern — your signature on the preserved digest is what makes the image verifiable inside your registry.

This is a deliberate assertion: you pulled this image, you verified it in the previous exercise, and you are admitting it into your environment on your own authority.
From this point on, everything in your registry — your application image and the vendor base you mirrored — is authenticated by the same key.

Because you used `--preserve-digests`, the digest in `~/python.digest` is Red Hat's original — you are signing the genuine artifact under your own key.

[source,bash,role=execute,subs=attributes+]
----
PYTHON_DIGEST=$(cat ~/python.digest)
cosign sign --tlog-upload=false \
  --yes --key cosign.key \
  registry-{guid}.{domain}/python@${PYTHON_DIGEST}
----

Now verify the mirrored image against your public key. The verification that failed in the previous exercise now succeeds.

[source,bash,role=execute,subs=attributes+]
----
cosign verify --insecure-ignore-tlog=true \
  --key cosign.pub \
  registry-{guid}.{domain}/python:3.12
----
----
Verification for registry-{guid}.{domain}/python:3.12 --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key
----

The image is the same one Red Hat published; the link attesting to it is now yours.
You have not recovered Red Hat's original signature -- you've established your own, which is what a downstream consumer of *your* registry actually needs to trust.

== Summary

Both images in your registry now carry a signature under a key you control.
A signature proves the image hasn't been tampered with since it was signed — but it says nothing about what's inside it.
In the next exercise you'll attach the SBOM you generated in an earlier exercise as a signed attestation, binding the package inventory to the same key so consumers can verify both the image and its contents.
