[[about-attestations]]
== What Is an Attestation?

An attestation is additional metadata about an image -- such as an SBOM, scan results, or build provenance -- that is:

1. Signed with the same key or identity as the image itself
2. Stored alongside the image in the registry as an OCI artifact
3. Verifiable by consumers before they run the image

By attaching the SBOM as a signed attestation, anyone can prove that the SBOM came from the same trusted source as the image. 
Attestations can be any metadata about the image, cryptographically verifiable via cosign. 
SLSA provenance for build environment information is another type of attestation.

[[attach-sbom]]
== Attach the SBOM as a Signed Attestation

[NOTE]
====
In Module 2, you generated the SBOM at `~/rhhi-demo.spdx` using `syft`. Attaching it here as a signed attestation ties it cryptographically to the specific image digest you pushed in Module 4.
====

Attach the SBOM using `cosign attest`, once again using the SHA digest. 
The `--predicate` flag points to the SBOM file, and `--type spdxjson` tells cosign the format.

[source,bash,role=execute,subs=attributes+]
----
cosign attest --tlog-upload=false \
  --yes --key cosign.key \
  --predicate ~/rhhi-demo.spdx --type spdxjson \
  registry-{guid}.{domain}/rhhi-demo@${IMAGE_DIGEST}
----
----
Using payload from: /home/rhel/rhhi-demo.spdx
----

The SBOM is now attached to the image in the registry and can be pulled for verification and examination separately but with cryptographic certainty that these are correct and related.

[[verify-attestation]]
== Verify the SBOM Attestation

We can pull the attestations via `cosign` from the registry to inspect the package contents of the image before we pull the image.
`cosign verify-attestation` returns the attestations as a base64 encoded envelope; pipe it through `jq` to extract the package list length.
Let's use the *tag* to pull the attestation, like we did with the signature.

[source,bash,role=execute,subs=attributes+]
----
cosign verify-attestation --insecure-ignore-tlog=true \
  --key cosign.pub \
  --type spdxjson \
  registry-{guid}.{domain}/rhhi-demo:hardened \
  | jq -r '.payload' | base64 -d | jq '.predicate.packages | length'
----
----
WARNING: Skipping tlog verification is an insecure practice that lacks of transparency and auditability verification for the signature.

Verification for registry-{guid}.{domain}/rhhi-demo:hardened --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key
69
----

The final number is the package count from the SBOM. This confirms:

* The attestation signature is valid
* The SBOM was signed by the holder of `cosign.key`
* The SBOM contains the package inventory that was created at build time

[[download-attestation]]
== Download the Attestation

You can also download the attestation envelope for offline inspection or use with compliance tooling.

[source,bash,role=execute,subs=attributes+]
----
cosign download attestation --output-file cosign.sbom \
  registry-{guid}.{domain}/rhhi-demo@${IMAGE_DIGEST}
----

The downloaded file can be decoded to standard JSON and can be processed with any JSON tool.

[source,bash,role=execute]
----
file cosign.sbom
----
....
cosign.sbom: JSON text data
....

[source,bash,role=execute]
----
jq -r '.payload' cosign.sbom | base64 -d | jq '.predicate.packages | length'
----
....
69
....

== Summary

You've established a complete chain of trust for your own container image:

* *Scanning*: Confirmed zero CVEs in the hardened image at ship time
* *SBOM*: Generated a machine-readable package inventory for compliance
* *Signature*: Proves the image hasn't been tampered with since it was signed
* *SBOM Attestation*: Proves the SBOM belongs to this specific image digest
* *Verification*: Anyone with the public key can verify the image and its SBOM

Every link you've added -- signature and attestation -- is one Red Hat also produces for the images you inherited. In the next module you'll look at the link that sits *before* yours: the build provenance the source attaches to prove where its images came from.

.*Production Best Practices*

* Use keyless signing with OIDC identity (GitHub Actions, GitLab CI, etc.)
* Store keys in KMS (AWS KMS, Azure Key Vault, GCP KMS, HashiCorp Vault)
* Enable the Rekor transparency log for audit trails
* Integrate `cosign verify` and `cosign verify-attestation` into admission controllers (Kyverno, OPA Gatekeeper)
* Signed SBOMs meet NIST and EU Cyber Resilience Act requirements
